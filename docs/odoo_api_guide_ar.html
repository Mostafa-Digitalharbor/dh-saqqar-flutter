الـ Odoo API هو الباب الرسمي اللي بيخلّي أي برنامج من بَرّه (تطبيق موبايل، سيرفر، سكريبت) يقدر يقرا ويكتب ويعدّل البيانات اللي جوّه Odoo بدون ما يفتح الواجهة بإيده. التيم ليد بعت 3 صفحات، وهي في الحقيقة موضوعين مختلفين:

① و ② → نفس الهدف (قراءة/كتابة الداتا) بس بطريقتين: واحدة قديمة (RPC) وواحدة جديدة (JSON-2).
③ → موضوع منفصل تمامًا: الـ Extract API، خدمة ذكاء اصطناعي بتقرا الفواتير والمستندات (OCR) وتطلّع بياناتها.

المصطلحبيعمل إيهالحالة

External JSON-2 APIنفس الوظيفة بشكل أحدث وأنضف (HTTP + JSON)الحالية / المستقبل

1 الـ External RPC API (الطريقة الكلاسيكية)

دي أقدم وأشهر طريقة. بتشتغل على بروتوكولين: XML-RPC و JSON-RPC. الفكرة إنك بتتكلم مع Odoo على 3 خطوات:

الخطوة 1 — تجهيز بيانات الدخول

  • url — لينك السيرفر، مثلاً https://mycompany.odoo.com
  • db — اسم الداتابيز
  • username — الإيميل
  • password — الباسورد (أو API key أأمن)

الخطوة 2 — Login عشان تاخد هويتك (uid)

import xmlrpc.client
common = xmlrpc.client.ServerProxy(f'{url}/xmlrpc/2/common')
uid = common.authenticate(db, username, password, {})  # بيرجع رقم هويتك
models = xmlrpc.client.ServerProxy(f'{url}/xmlrpc/2/object')

الخطوة 3 — تشتغل على الداتا عن طريق execute_kw

كل العمليات بتتعمل بدالة واحدة زي الريموت كنترول: «روح للموديل الفلاني واعمل العملية الفلانية». دي العمليات الأساسية (الـ CRUD):

# 🔍 search — دوّر (بيرجّع IDs بس)
ids = models.execute_kw(db, uid, password, 'res.partner',
    'search', [[['name', '=', 'John']]], {'limit':10, 'offset':0})

# 📖 read — اقرا بيانات IDs معيّنة
data = models.execute_kw(db, uid, password, 'res.partner',
    'read', [ids], {'fields':['name','email','phone']})

# ⚡ search_read — دوّر واقرا في خطوة واحدة (الأكثر استخدامًا)
# ➕ create — اعمل ريكورد جديد
new_id = models.execute_kw(db, uid, password, 'res.partner',
    'create', [{'name':'Acme', 'email':'a@acme.com'}])

# ✏️ write — عدّل   |   🗑️ unlink — امسح
models.execute_kw(db, uid, password, 'res.partner', 'write', [ids, {'phone':'+20100'}])
models.execute_kw(db, uid, password, 'res.partner', 'unlink', [ids])

حاجتين لازم تفهمهم كويس

أ) الـ Domain (الفلتر): بيتكتب ['field', 'operator', 'value'] — يعني ['name','=','John']. ده زي الـ WHERE في SQL بالظبط، وتقدر تجمع أكتر من شرط في ليستة.

ب) الـ Pagination: متجبش كل الداتا مرة واحدة، استخدم limit و offset عشان تجيبها على دفعات. وفيه كمان search_count للعدّ بس، و fields_get لمعرفة حقول الموديل.

⚠️ تحذير الإهلاك (Deprecation) بروتوكولات /xmlrpc و /xmlrpc/2 و /jsonrpc هتتشال رسميًا: في Odoo Online شتاء 2027 (نسخة 21.1)، وفي النسخة العادية خريف 2028 (Odoo 22). فالجديد يُبنى على JSON-2.

2 الـ External JSON-2 API (الطريقة الجديدة = المستقبل)

نفس فكرة RPC بالظبط، بس بشكل أحدث وأنضف وأنسب لتطبيقات الموبايل لأنها HTTP + JSON عادي.

أهم 3 اختلافات

  1. لكل عملية URL مباشر بدل execute_kw المعقّدة:
    POST /json/2/<model>/<method> — مثلاً POST /json/2/res.partner/search_read
  2. مفيش login منفصل — بتبعت الـ API key مباشرة في الهيدر.
  3. كل المعاملات بالاسم (named) — مفيش ترتيب معاملات يلخبط زي القديم.
POST /json/2/res.partner/search_read
Authorization: bearer <api_key>
Content-Type: application/json
X-Odoo-Database: mycompany

{
  "domain": [["country_id", "=", 65]],
  "fields": ["name", "email"],
  "limit": 10
}

3 الـ Extract API (موضوع منفصل — OCR للمستندات)

دي مالهاش علاقة بقراءة/كتابة الداتا العادية. دي خدمة بتاخد صورة أو PDF لمستند وتطلّع بياناته منظّمة أوتوماتيك باستخدام OCR + AI.

نوع المستندبتستخرج منه
الفواتير (Invoices)الإجمالي، تاريخ الاستحقاق، الأصناف، بيانات المورّد
كشوف الحساب البنكيةالرصيد الافتتاحي/الختامي، تواريخ المعاملات
المصاريف (Expenses)المبالغ، التواريخ، التصنيف
السير الذاتية (CVs)الأسماء، بيانات التواصل، المؤهلات

بتشتغل على مرحلتين (Asynchronous):

  1. POST /parse — تبعت المستند، يرجّعلك document_token (زي رقم تذكرة).
  2. POST /get_result — تسأل بالتوكن «خلص ولا لسه؟» لحد ما تجيب النتيجة (أو بتوصلك على Webhook).

Base: https://extract.api.odoo.com · البروتوكول: JSON-RPC 2.0

💳 خدمة مدفوعة الـ Extract API خدمة IAP مدفوعة بالكريدت — كل مستند بيتقرا بياكل كريدت واحد. مش بنستخدمها إلا لو فعلًا عندنا فواتير/إيصالات عايزين نقراها أوتوماتيك.

4 القيود المهمة (لازم تعرفها قبل أي شغل)

🔒 الأهم: الـ API مقفول على خطة Custom بس الـ External API (بكل أنواعه) متاح فقط على خطة Custom، ومش متاح خالص على One App Free ولا Standard.

تفصيلة مهمة: القفل ده على إن «برنامج من بَرّه يكلّم Odoo» — وده بالظبط اللي بنعمله من Flutter. لكن لو Odoo هو اللي بيكلّم خدمة خارجية (Stripe / PayPal / شركات شحن) ده مسموح على Standard. السيناريو بتاعنا محتاج Custom plan أكيد.
🚦 حدود الاستخدام (Rate Limits)
  • القاعدة العامة: حوالي طلب واحد في الثانية وبدون طلبات متوازية.
  • على نسخة الـ SaaS: حوالي 60 طلب في الدقيقة.
  • عمليًا: نتجنّب الـ polling السريع، ونعمل backoff & retry، ونستخدم pagination و bulk fetch بدل طلب لكل ريكورد.

5 الأمان وإدارة الـ API Key

إزاي تعمل API Key

My Profile (فوق) ← تاب Account Security ← Generate API Key ← تدخل الباسورد ← تكتب وصف. الـ key بيظهر مرة واحدة بس (مفتاح عشوائي 160-bit) ومش هتقدر تشوفه تاني — انسخه فورًا.

✅ أفضل الممارسات
  • اعمل مستخدم مخصّص للتكامل بأقل صلاحيات يحتاجها (مش admin).
  • Key منفصل لكل خدمة عشان لو واحد اتسرّب تلغيه لوحده.
  • HTTPS دايمًا + تدوير (rotation) دوري للمفتاح، ولو اتسرّب امسحه فورًا.
  • متحطش الـ key في كود الموبايل أبدًا — أي حد يقدر يستخرجه من التطبيق.

التصميم الموصى به لتطبيق صقّار: الموبايل يكلّم الـ backend بتاعنا، والـ backend هو اللي يحتفظ بالـ API key ويكلّم Odoo. كده المفتاح ميبانش في التطبيق نهائيًا — وده متوافق مع الـ architecture المتفق عليه.

6 أسئلة التيم ليد المتوقّعة + الإجابات

نستخدم RPC القديمة ولا JSON-2؟
JSON-2 للمشاريع الجديدة على Odoo 19. أنضف، أكواد حالة صح، API key بدل login، ومناسبة لـ Flutter. RPC بس لو محتاجين ندعم نسخ أقدم (14–18). والقديمة هتتشال 2027–2028.
إيه اللي محتاجينه عشان نبدأ التكامل؟
(1) اشتراك Odoo Custom، (2) لينك السيرفر + اسم الداتابيز، (3) مستخدم تكامل مخصّص بصلاحيات محدودة، (4) API key متخزّن في الـ backend بتاعنا.
إزاي بنقرا ونكتب البيانات؟
عن طريق العمليات القياسية على الموديلات: search_read للقراءة، create للإضافة، write للتعديل، unlink للحذف — مع فلتر domain و pagination.
فيه حدود على عدد الطلبات؟
أيوه — حوالي طلب/ثانية (أو 60/دقيقة على SaaS) وبدون طلبات متوازية. بنتعامل معاها بـ backoff/retry + bulk fetch + pagination.
آمن نحط الـ key في تطبيق الموبايل؟
لأ. الموبايل يكلّم الـ backend، والـ backend يكلّم Odoo بالمفتاح. مستخدم محدود الصلاحيات + HTTPS + تدوير دوري للمفتاح.
الـ API key بيقع لوحده؟
في JSON-2 المفتاح الافتراضي بيعيش 90 يوم ثم يموت؛ الـ admin يقدر يعمل مفتاح دائم. لازم خطة لتجديده.
إيه الـ Extract API وهل نستخدمه؟
خدمة OCR+AI لاستخراج بيانات الفواتير/الإيصالات/الـ CV، مدفوعة بالكريدت. نستخدمها فقط لو عندنا حالة استخراج مستندات فعلية — مش مطلوبة للتكامل العادي.

⭐ الخلاصة في 6 نقط

  • JSON-2 هو المستقبل — RPC القديمة هتتشال (2027–2028).
  • JSON-2 أسهل لـ Flutter: HTTP + JSON + API key بدل login.
  • ⚠️ محتاجين خطة Custom — نتأكد منها قبل أي وعود.
  • 🚦 في rate limits (~1/ثانية) — نصمّم بـ backoff + pagination.
  • 🔐 الـ key في الـ backend مش في الموبايل + مستخدم محدود الصلاحيات.
  • 📄 الـ Extract API موضوع منفصل (OCR مدفوع) — مش جزء من التكامل الأساسي.
