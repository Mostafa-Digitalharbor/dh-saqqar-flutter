صقّار يشتغل من غير نت

Offline-First Cache + Outbox💚 محايد للتوكينز · بيوفّر داتا وبطارية
⚠️ المشكلة (مؤكدة من الكود)
مفيش أي قاعدة بيانات محلية (لا drift/isar/sqflite/hive). كل شاشة بتجيب من الـ API مباشرة → لو فتحت التطبيق في مخزن/مصنع شبكته ضعيفة = شاشة فاضية. مفارقة: المنتج بيتباع كـ«native superpowers» وهو offline أضعف من المتصفح.
💡 الفكرة
  • قاعدة بيانات محلية (Drift/Isar) تكاش المحادثات + الرسائل + ميتاداتا الـ artifacts → فتح فوري بدون spinner وقراءة كاملة offline.
  • Outbox: الرسائل/الموافقات اللي اتكتبت offline تتصفّ وتتبعت أوتوماتيك أول ما النت يرجع.
  • Optimistic UI: رسالتك تظهر فوراً وتتأكّد بعدين.
⚙️ العمق التقني
جداول conversations + messages + outbox في Drift؛ الـ ChatCubit يقرا من الكاش أولاً (instant paint) وبعدين delta-fetch بالـ ?since= cursor الموجود أصلاً. مزامنة عند الـ reconnect (نبني على connectivity_cubit.dart بدل الاكتفاء بالـ banner).
📈 الأثر
فتح فوري · قراءة offline · توفير داتا وبطارية (كاش + deltas) · مرونة في أسوأ شبكة — وده بالظبط جمهور الـ ERP الميداني.
②

بث حي بدل السؤال كل ثانية ونص

Real-time SSE streaming (replaces polling)💚 محايد لتوكينز الـ LLM · بيوفّر حِمل سيرفر وبطارية
⚠️ المشكلة (مؤكدة)
chat_cubit.dart بيعمل Timer.periodic كل 1.5 ثانية طول ما الوكيل شغّال = ~40 request/دقيقة بتضرب السيرفر، تستنزف البطارية والداتا، وبتأخّر نص الرد لحد ثانية ونص. وعقد الباك إند أصلاً فيه SSE متعرّف بالكامل (§7) — الموبايل بس لسه مش مطبّقه.
💡 الفكرة
نطبّق SSE client حسب العقد: التوكينز تظهر لحظياً (typing حقيقي)، ونوقف الـ poll وقت البث (نسيب poll خفيف كـ fallback للـ reconnect).
⚙️ العمق التقني
Dio بـ ResponseType.stream + utf8.decoder + LineSplitter (مذكور في العقد §7) → معالجة أحداث token/tool_call/tool_result/approval_required/done + عقد إعادة الاتصال (resume mid-run).
📈 الأثر
نص فوري وسلس · تقليل ضخم في عدد الـ requests (توفير infra حقيقي) · بطارية وداتا أقل بكتير.
⚠️ ملاحظة صدق للتيم ليد: فيه اعتماد على الباك إند (قرار الـ SSE لسه pending في العقد). شغل العميل جاهز نعمله، بس محتاجين الباك إند يفعّل الـ endpoint.
③

قفل بصمة + تأكيد الموافقات الخطيرة

Biometric App-Lock + secure approval re-auth💚 محايد للتوكينز · أمان enterprise · بيكمّل #2 و#3
⚠️ المشكلة (مؤكدة)
مفيش local_auth ولا أي قفل. التطبيق فيه خزنة بتكتب على Odoo إنتاج وبتشغّل shell. لو حد خطف موبايلك وهو مفتوح → يقدر يوافق على فعل مدمّر أو يبص على الخزنة. ثغرة أمان حقيقية، خصوصاً للمؤسسات.
💡 الفكرة
  • قفل Face ID / بصمة عند فتح التطبيق (اختياري + قفل تلقائي بعد الـ background).
  • إعادة تحقق بيومتري قبل الأفعال عالية الخطورة (odoo_write / server_command) وقبل فتح/تعديل الخزنة.
⚙️ العمق التقني
حزمة local_auth + gate في الـ router/AuthCubit؛ خطّاف قبل POST /approvals/{id}/decision/ للأفعال عالية الخطورة (الـ risk field موجود أصلاً من #1 المعتمد).
📈 الأثر
أمان على مستوى الجهاز · بيربط بقصة #2 (السجل): «مين وافق؟» تبقى «اللي وافق متحقّق ببصمته» · بيكمّل #3 (SoD). عامل بيع قوي للمؤسسات.
④

صوّر / امسح وابعت للوكيل

In-app Camera + Document Scanner💚 محايد للتوكينز · قدرة نيتيف الويب مايقدرش يعملها
⚠️ المشكلة (مؤكدة)
chat_screen.dart بيستخدم file_picker بس — اختيار ملفات موجودة، مفيش كاميرا ولا ماسح. بس استخدام الـ ERP الميداني كله تصوير: أمين المخزن بيصوّر إذن استلام، المحاسب بيصوّر فاتورة مورّد، حد بيمسح ليبل منتج.
💡 الفكرة
كاميرا + ماسح مستندات (كشف حواف، متعدد الصفحات → PDF) جوه الـ composer مباشرة → للوكيل. بعدها الوكيل يقرا الفاتورة (OCR) ويعمل منها vendor bill في Odoo مثلاً.
⚙️ العمق التقني
image_picker (كاميرا) + حزمة document-scanner (نيتيف iOS VisionKit / Android ML Kit). نفس مسار الـ attachments الموجود — بس مصدر جديد للملف.
📈 الأثر
بيحوّل كاميرا الموبايل لأداة إدخال بيانات ERP — قدرة نيتيف حقيقية الويب عمره ما هيعملها. قيمة هائلة للمخازن واللوجستيك والريتيل.
⑤

إشعار للموافقات (مش مراقبة) + Live Activity

Approval Push + Live Activity / ongoing notification💚 محايد للتوكينز تماماً — النص الآمن من فكرة #3
⚠️ المشكلة (مؤكدة)
devices_api.dart scaffold فاضي، مفيش firebase_messaging. النهاردة الموافقات المعلّقة بتبان بس لما تفتح التطبيق وتـ poll. لو بدأت run وقفلت الموبايل والوكيل وقف مستني موافقتك → ممكن تفضل عالقة ساعات.
💡 الفكرة
Push (FCM/APNs) بس للموافقات وإتمام الـ run اللي إنت بدأته → كبسة تفتحلك كارت الموافقة. + Live Activity (iOS) / إشعار مستمر (Android) بيوريك «الوكيل شغّال…» مع زرار Stop.
🔑 الفرق الحاسم عن #3: ده إشعار لـ run إنت بدأته — الشغل اتعمل أصلاً، صفر توكينز زيادة. مش مراقبة استباقية (اللي كانت بتشغّل الوكيل لوحدها وتستهلك). ده النص الآمن من الفكرة — بيحيي الـ scaffold المحجوز من غير أي قلق تكلفة.
📈 الأثر
الـ runs تبقى async موثوقة (ابدأ، اقفل الموبايل، هتتنبّه لما يحتاجك) · وبيقلّل polling البطارية كمان.

★ الترابط والترشيح

تحسينات الموبايل بتقوّي المعتمد — مش منفصلة عنه:

✅ #1 محاكاة✅ #2 سجل←الأساس اللي بيتبني عليه
③قفل البصمة = «اللي وافق متحقّق ببصمته» → يقوّي audit trail بتاع #2
⑤إشعار الموافقات = النص الآمن من #3 الملغاة (صفر توكينز)
④الكاميرا = مصدر إدخال جديد بيغذّي الوكيل بداتا الميدان
①②Offline + SSE = الأساس اللي بيخلّي كل الشاشات أسرع وأرخص تشغيل
الترتيب اللي يبهر:
  1. ① Offline-First — بيحسّن كل شاشة فوراً، وأكبر فجوة «أضعف من الويب».
  2. ② SSE — أكبر قفزة في الإحساس + توفير infra (بس فيه اعتماد باك إند).
  3. ⑤ Push للموافقات — أعلى أثر مقابل أقل مجهود، token-neutral، وبيحيي scaffold موجود.
  4. ③ Biometric — أمان enterprise، بيكمّل #2/#3.
  5. ④ Camera/Scanner — أقوى native superpower للعرض الميداني.
الخلاصة
أقوى ثنائي للعرض: ① + ⑤ — واحد بيخلّي التطبيق يشتغل في أي شبكة، وواحد بيخلّيه موثوق وانت قافله. الاتنين token-neutral، فمستحيل يتلغوا زي #3 — وكلهم بيحوّلوا الموبايل من «نسخة مرافقة» لـ «السبب اللي تختار صقّار عشانه».
